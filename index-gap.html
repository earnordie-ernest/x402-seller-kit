You shipped a paid x402 route. It answers 402. A buyer could pay it. But when you search for it in agent tooling — agentcash search, the x402scan explorer, anything that discovers through the Coinbase CDP Bazaar — it is not there. register reported success. So why are you invisible?

Because the Bazaar is not a directory you submit to

This is the part most sellers miss. Coinbase's own documentation is explicit: there is no registration form and no submit API. A row appears in the CDP Bazaar only when a route is discovered and settles at least one payment through the CDP facilitator. The /platform/v2/x402/discovery/* endpoints are read-only.

That means agentcash register, x402scan and MPPScan write rows to their own listing databases. The CDP Bazaar is a different catalogue, fed by facilitator settlement. A route can be "registered" everywhere and still have zero CDP rows — which is the catalogue most agent tooling actually searches.

How to check yours (two commands)

Read your live payTo from the 402, then ask the catalogue for it directly:

# 1. your live challenge (v2 puts the whole object in the base64 PAYMENT-REQUIRED header)
curl -si -X POST 'https://YOUR-HOST/your/paid/path' | grep -i payment-required
# decode that base64 -> accepts[0].payTo

# 2. does the catalogue hold a row for that payTo?
curl -s 'https://api.cdp.coinbase.com/platform/v2/x402/discovery/merchant?payTo=0xYOURPAYTO&limit=100&offset=0'
#   -> "pagination":{"total":N}   N=0 means zero rows.
Always run a control. Query a payTo you know is indexed (a large seller). If the control returns rows and yours returns 0, the zero is real. If the control is also zero, your query is broken and you must not conclude anything.

The three causes of a zero-row payTo

CauseWhat it looks likeFix
1. Non-CDP facilitator You settle via PayAI, FluxA, or self-facilitate. Your /settle succeeds, but the settlement never reaches CDP, so no row is ever written. Settle ≥1 real payment through the CDP facilitator for the route, then re-query the merchant endpoint above. If a row appears, this was it.
2. v2-only challenge The whole payment object is in the base64 PAYMENT-REQUIRED header, with no v1 JSON body (accepts[]). Ingest that reads the v1 body sees nothing. Emit a v1-compatible 402 body (an accepts[] array) alongside the header, or confirm your facilitator writes the declaration.
3. Path-scoped origin You are a serverless function (e.g. a Supabase Edge Function) at /functions/v1/…. Origin discovery normalises to the bare host and probes /openapi.json at the root, which cannot exist. Serve /.well-known/x402 at the function base (the crawler follows it), and ask the explorer team to accept your full OpenAPI URL for ingest.

Tell them apart in one step

Decode the EXTENSION-RESPONSES header on your /verify and /settle replies (base64 JSON). If the bazaar extension is absent or says rejected, the declaration never reached the facilitator — that is cause 1, not a UI problem.
